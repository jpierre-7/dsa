Why in can be slow

Counting steps, and your first Big-O

Today's win You'll take a function that gets 4× slower every time its input doubles, rewrite it so it only gets 2× slower, and measure the difference yourself. Along the way you'll learn to read the notation O(n) and O(n²).

Guess first

This is the kind of code that ships every day. It drops messages from blocked senders:

blocked = load_blocked_ids()     # a list of 100,000 ids
for msg in messages:              # 100,000 messages
    if msg.sender_id in blocked:
        drop(msg)

Before you read on, guess: in the worst case, roughly how many comparisons does this make? Commit to a number, even a rough one.Guessing before you're taught is called pretesting. A wrong guess still helps you remember the answer when you see it.

Reveal

Up to 10 billion. That's 100,000 messages times up to 100,000 comparisons each. A one-line change brings it down to roughly 100,000 steps. By the end of this lesson you should be able to find that line yourself.

1. Count steps, not seconds

Timing depends on your laptop, but the number of steps an algorithm takes doesn't. So we measure cost as a count of basic steps, written as a function of n, the size of the input.

x in some_list looks like one operation, but Python has to check the items one at a time until it finds x. If x isn't there, which is the worst case, it checks all n items. So its cost grows in step with n.

x in some_set works differently. A set jumps almost straight to where x would be, so on average it takes about the same small number of steps whether the set holds ten items or ten million.How a set manages this is called hashing, and it gets its own lesson. For now, trust the table: the Python Wiki's TimeComplexity page lists list x in s as O(n) and set x in s as O(1) average.

2. Big-O is the shape of that growth

Big-O notation keeps only the part of the step count that matters when n gets large:Miller & Ranum put it this way: Big-O classifies an algorithm by "its dominant process with respect to the size of the problem." See §2.3 Big-O Notation.

  1. Keep the dominant term. 3n² + 5n + 100 is O(n²). Once n is large, the n² term dwarfs everything else.
  2. Drop constant factors. 2n is O(n), and so is n/2. Constants depend on the machine; the shape of the growth doesn't.

So x in list is O(n), read "order n" or "linear". x in set is O(1), "constant time", on average.

3. Nested loops multiply

Code that runs one loop after another adds the costs: n + n = 2n, which is O(n). A loop inside another loop multiplies them: n × n = O(n²), "quadratic".

The catch is that some loops don't look like loops. In the opening example there's only one for, but in blocked hides a second loop over a list, so the whole thing is O(n²). Here's the same pattern with both loops visible:

def has_duplicates_slow(items):
    for i in range(len(items)):
        for j in range(i + 1, len(items)):   # loop inside a loop
            if items[i] == items[j]:
                return True
    return False

The inner loop starts at i + 1, so this compares about n²/2 pairs, not n². That's still O(n²), because dropping the ½ is exactly rule 2.

4. Feel the difference

Drag the slider. Somewhere past n = 10,000, quadratic code stops being a small delay and becomes an outage.

On the machine this lesson was written on, the slow duplicate check ran about 25 million comparisons a second, so 10⁷ steps per second is a slightly cautious round figure.

5. Do it: make it O(n)

  1. Open exercises/0001_has_duplicates.py.
  2. Fill in has_duplicates_fast. You may only loop over items once. Try it without looking back at the lesson.
  3. Run python3 exercises/0001_has_duplicates.py. It checks your answers, then times both versions as n doubles.

What to look for: each time n doubles, the slow version takes about ×4 as long, and yours takes about ×2. This doubling test is a quick way to identify a growth rate from measurements: ×2 means O(n), ×4 means O(n²).

Why this matters for you

At work: any time you see in, .index() or .remove() on a list inside a loop, check whether it's a hidden O(n²).
In interviews: a common first improvement to a brute-force answer is to replace a repeated O(n) lookup with an O(1) set or dict lookup. As the Tech Interview Handbook puts it, checking membership in a hash table "is O(1) on average."

Check yourself

Try these from memory. The effort of recalling is what makes it stick.

1. emails is a list of n strings. In the worst case, how does the cost of x in emails grow?

  • O(1)
  • O(n)
  • O(n²)
  • O(2ⁿ)

A list is scanned item by item. If x isn't present, every one of the n items is checked.

2. You convert it with emails_set = set(emails). What's the average cost of x in emails_set?

  • O(1)
  • O(n)
  • O(n²)
  • O(n³)

Set membership is O(1) on average, per the Python Wiki. Building the set costs O(n) once, so it pays off when you look things up many times.

3. a and b are both lists of length n. What's the Big-O of [x for x in a if x in b]?

  • O(1)
  • O(n)
  • O(n²)
  • O(n³)

There's one visible loop over a, and in b hides a second loop over a list. Nested loops multiply: n × n. Making b a set brings it down to O(n).

4. A function loops over a list once to find the max, then loops over it again to count how many items equal that max. What's its Big-O?

  • O(1)
  • O(n)
  • O(2n)
  • O(n²)

These loops run one after the other, so their costs add: n + n = 2n. Dropping the constant factor gives O(n). You'd never write O(2n) as a final answer.

5. An O(n²) function takes 1 second at n = 10,000. Roughly how long will it take at n = 20,000?

  • 1 s
  • 2 s
  • 4 s
  • 8 s

Doubling n multiplies n² by 2² = 4. This is the doubling test from the exercise, run in reverse.
